## Pengantar

Coba buka lagi layar-layar `kuliah-app` yang kamu tulis di [Menampilkan Data](/belajar/fullstack/read-data),
[Create & Update](/belajar/fullstack/create-update), dan [Delete & Optimistic Update](/belajar/fullstack/delete-optimistic).
Hampir setiap layar punya pola yang sama:

- tiga `useState`: untuk data, untuk status loading, dan untuk error,
- `useEffect` atau `useFocusEffect` yang memanggil `apiFetch`,
- `AbortController` untuk membatalkan request lama,
- salinan data dan pengembalian manual (rollback) kalau hapus gagal.

Kodenya jalan. Tapi makin banyak layar, makin terasa masalahnya:

- **Kode berulang.** Urutan "ambil data, nyalakan loading, tangkap error" kamu tulis ulang di empat layar.
- **Request dobel.** Layar edit meminta tugas yang sama persis dengan yang baru saja dimuat layar detail.
- **Request yang sia-sia.** Supaya tugas baru ikut tampil, daftar diambil ulang setiap kali layarnya muncul.
  Padahal sering kali tidak ada yang berubah.
- **Mudah menyerah.** Wi-Fi kampus putus dua detik, dan layar langsung menampilkan error. Tidak ada
  percobaan ulang.

Di pelajaran ini kamu memindahkan semua urusan itu ke **TanStack Query** (dulu bernama React Query).
TanStack Query adalah **library** (kumpulan kode siap pakai buatan orang lain) yang khusus mengurus
**server state**, yaitu data milik server yang sedang ditampilkan di HP. Selain tiga tujuan di atas, kamu
juga akan mengatur `gcTime`, retry (mencoba ulang request yang gagal), dan **refetch** (mengambil ulang data
dari server) saat aplikasi kembali dibuka.

Kita memakai **TanStack Query v5** di proyek Expo SDK 58 berbahasa JavaScript.

## Server state berbeda dengan client state

<Callout type="analogi" title="Catatan pribadi vs foto jadwal di papan pengumuman">

Coretan di buku catatanmu hanya kamu yang bisa mengubah. Isinya pasti sama dengan yang kamu tulis.

Jadwal kuliah lain cerita. Jadwal aslinya tertempel di papan pengumuman jurusan, lalu kamu memotretnya
dengan HP. Besoknya bagian akademik memindahkan kelas Basis Data ke ruang lain. Foto di HP-mu tidak ikut
berubah. Foto itu sudah **basi**, dan kamu baru tahu setelah melihat papan lagi.

- Buku catatan pribadi = **client state**
- Papan pengumuman jurusan = server dan database
- Foto jadwal di HP = **server state**, salinan yang bisa basi kapan saja

</Callout>

**State** adalah data yang bisa berubah dan ikut menentukan isi layar. Ada dua jenis. Teks yang sedang
diketik di form adalah **client state**. Data itu sepenuhnya milik aplikasi, dan tidak ada pihak lain yang
bisa mengubahnya. Daftar tugas adalah **server state**. Data aslinya ada di database API pendamping. Yang
ada di HP hanyalah salinan, dan salinan itu bisa basi kapan saja. Misalnya kamu mengubah tugas dari tablet,
token login kedaluwarsa, atau server sedang restart.

| Aspek | Client state | Server state |
| --- | --- | --- |
| Pemilik | Aplikasi | Server (database) |
| Contoh di `kuliah-app` | Input form, filter yang dipilih, modal terbuka | Daftar tugas, detail tugas, daftar mata kuliah |
| Bisa basi? | Tidak | Ya, kapan saja |
| Perlu loading dan error? | Jarang | Selalu |
| Alat yang cocok | `useState`, `useReducer`, context | TanStack Query |

`useState` dirancang untuk kolom kiri. Kalau kita memaksanya mengurus kolom kanan, kita harus menulis sendiri
banyak hal:

- **cache**: tempat menyimpan salinan data supaya tidak perlu diminta ulang ke server,
- **deduplikasi**: menggabungkan request yang sama persis menjadi satu,
- **retry**: mencoba lagi request yang gagal,
- **sinkronisasi ulang**: mengambil data terbaru saat salinan mungkin sudah basi.

TanStack Query sudah menyediakan semuanya. Bandingkan kodenya:

<Compare>
<CompareItem title="Sebelum: semua diurus manual" tone="bad">

```jsx
const [task, setTask] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

useEffect(() => {
  const controller = new AbortController();
  apiFetch(`/api/tasks/${id}`, { signal: controller.signal })
    .then((json) => setTask(json.data))
    .catch((err) => setError(err))
    .finally(() => setLoading(false));

```

</CompareItem>


Satu baris ini menggantikan semua kode di kiri. Cache, pembatalan request, retry, dan refetch otomatis diurus
di dalam hook `useTask`. Hook itu kamu tulis sekali saja di `src/features/tasks/queries.js`.

## Cara kerja cache TanStack Query

<Callout type="analogi" title="Seperti catatan jawaban di papan tulis kelas">

Teman sekelas sering bertanya ke ketua kelas, "Tugas Basis Data dikumpul kapan?" Daripada menghubungi dosen
setiap kali ditanya, ketua kelas bertanya sekali. Jawabannya ia tulis di papan tulis dengan judul "Deadline
Basis Data", lengkap dengan jam penulisan.

- Papan tulis = **cache**
- Judul catatan = **query key**
- Bertanya ke dosen = request ke server (`queryFn`)
- Catatan yang baru ditulis dan masih bisa dipercaya = **fresh**
- Catatan yang sudah agak lama: tetap boleh dibaca, tapi akan dicek ulang ke dosen saat ada kesempatan = **stale**
- Catatan yang tidak dibaca siapa pun lagi, lalu dihapus setelah beberapa waktu = **inactive** dan `gcTime`

Bedanya, ketua kelas bisa lupa mengecek ulang. TanStack Query mengecek ulang otomatis sesuai aturan yang
kamu pasang.

</Callout>

TanStack Query menyimpan setiap data di cache dengan sebuah **query key**. Query key adalah array yang menjadi
nama unik data itu, misalnya `["tasks", "detail", 5]`. Dua komponen yang memakai key yang sama berbagi satu
catatan di cache dan satu request. Jadi kalau layar detail dan layar edit sama-sama meminta tugas 5,
request-nya hanya dikirim sekali.

Setiap catatan di cache (disebut **entri cache**) melewati siklus berikut:

<Flow nodes={["Query baru", "fetching", "fresh", "stale", "inactive", "dihapus"]} labels={["queryFn jalan", "data tiba", "lewat staleTime", "tak ada layar pemakai", "lewat gcTime"]} caption="Siklus hidup satu entri cache" />

- **fresh** (segar): data dianggap masih baru. TanStack Query tidak akan mengambilnya ulang.
- **stale** (basi): data tetap ditampilkan, tapi akan diambil ulang diam-diam di latar belakang saat ada
  pemicu. Contoh pemicu: layar baru memakai key itu, aplikasi kembali dibuka, atau koneksi pulih.
- **inactive** (tidak terpakai): tidak ada komponen yang memakai key itu. Data masih disimpan selama `gcTime`.
  Kalau layarnya dibuka lagi dalam waktu itu, isinya langsung tampil tanpa spinner.

Ini nilai bawaan di v5 yang perlu kamu ingat:

| Opsi | Bawaan | Artinya |
| --- | --- | --- |
| `staleTime` | `0` | Data langsung dianggap basi begitu tiba |
| `gcTime` | 5 menit | Lama data inactive disimpan sebelum dibuang |
| `retry` (query) | `3` | Query gagal dicoba ulang 3 kali dengan jeda 1, 2, lalu 4 detik |
| `retry` (mutation) | `0` | Mutation tidak pernah diulang otomatis |
| `refetchOnWindowFocus` | `true` | Ambil ulang data basi saat aplikasi kembali dibuka |
| `refetchOnReconnect` | `true` | Ambil ulang data basi saat koneksi pulih |
| `refetchOnMount` | `true` | Ambil ulang data basi saat komponen baru memakai key-nya |

Bawaan `staleTime: 0` aman, karena data selalu dicek ulang. Tapi boros: setiap kali layar detail dibuka,
request baru dikirim. Daftar tugas kuliah jarang berubah dalam hitungan detik. Jadi 30 detik adalah angka
tengah yang masuk akal.

<Callout type="info" title="Di React Native tidak ada 'window'">

Di browser, TanStack Query tahu kapan tab kembali dibuka dan kapan internet putus. Info itu datang dari
objek `window` milik browser. React Native tidak punya `window`. Akibatnya `refetchOnWindowFocus` dan
`refetchOnReconnect` tidak pernah terpicu, sampai kita menyambungkannya sendiri: `focusManager` ke `AppState`
(status aplikasi: sedang dibuka atau di latar belakang) dan `onlineManager` ke status jaringan. Itu yang kita
lakukan di langkah berikutnya.

</Callout>

## Memasang TanStack Query di kuliah-app

<Steps>
<Step title="Instal paket">

Jalankan dari folder `kuliah-app`. `npx expo install` memilih versi paket yang cocok dengan SDK 58.
`expo-network` (paket untuk membaca status jaringan HP) sudah termasuk di Expo Go. Jadi kamu tidak perlu
membuat development build (versi aplikasi Expo yang kamu build sendiri).

```bash
npx expo install @tanstack/react-query expo-network
```

</Step>
<Step title="Buat src/lib/query-client.js">

File ini melakukan tiga hal. Pertama, membuat satu `QueryClient`, yaitu pengelola cache untuk seluruh
aplikasi. Kedua, menetapkan aturan bawaan. Ketiga, menghubungkan TanStack Query ke status aplikasi dan
status jaringan HP.

```js title="src/lib/query-client.js" showLineNumbers
import { AppState, Platform } from "react-native";
import { QueryClient, focusManager, onlineManager } from "@tanstack/react-query";
import * as Network from "expo-network";
import { ApiError } from "./api";

function shouldRetry(failureCount, error) {
  // 4xx berarti request-nya yang salah (validasi, 404, token). Diulang pun hasilnya sama.
  if (error instanceof ApiError && error.status >= 400 && error.status < 500) {
    return false;
  }
  return failureCount < 2;
}

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30 * 1000,
      retry: shouldRetry,
    },
  },
});

AppState.addEventListener("change", (status) => {
  if (Platform.OS !== "web") {
    focusManager.setFocused(status === "active");
  }
});

onlineManager.setEventListener((setOnline) => {
  let initialized = false;
  const subscription = Network.addNetworkStateListener((state) => {
    initialized = true;
    setOnline(!!state.isConnected);
  });
  Network.getNetworkStateAsync()
    .then((state) => {
      if (!initialized) setOnline(!!state.isConnected);
    })
    .catch(() => {});
  return () => subscription.remove();
});
```

Penjelasan per bagian:

- **Baris 6–12, `shouldRetry`**: memutuskan apakah request yang gagal dicoba lagi. Error 4xx (kode status
  400–499) berarti request kita yang salah, misalnya data tidak valid, tugas tidak ada, atau token salah.
  Dicoba ulang pun hasilnya sama, jadi langsung dikembalikan ke layar. Error lain dicoba ulang. `failureCount`
  mulai dari `0` untuk kegagalan pertama, jadi `failureCount < 2` berarti maksimal dua kali ulang (total tiga
  percobaan). Hasilnya, pengguna tidak perlu menunggu sekitar 7 detik hanya untuk melihat "Tugas tidak ditemukan".
- **Baris 14–21**: membuat `QueryClient` dengan `staleTime` 30 detik dan aturan retry tadi.
- **Baris 23–27, `AppState`**: setiap status aplikasi berubah, kita memberi tahu `focusManager`. Saat kamu
  kembali dari WhatsApp ke `kuliah-app`, status menjadi `active`, lalu query yang basi diambil ulang.
- **Baris 29–41, `onlineManager`**: kita mengajari TanStack Query cara membaca status jaringan.
  `addNetworkStateListener` memberi kabar setiap kali koneksi berubah, dan `getNetworkStateAsync` membaca
  status awal saat aplikasi baru dibuka. Saat offline, query baru tidak gagal. Query itu **dijeda**
  (`fetchStatus: "paused"`) dan jalan sendiri begitu koneksi kembali.

</Step>

<Callout type="warning" title="Pakai isConnected, bukan isInternetReachable">

`expo-network` memberi dua tanda. `isConnected` artinya HP tersambung ke jaringan, misalnya Wi-Fi.
`isInternetReachable` artinya HP bisa menjangkau internet. Selama pengembangan, API pendamping berjalan di
laptopmu, di Wi-Fi yang sama dengan HP. Wi-Fi kos yang kuotanya habis tetap bisa menyambungkan HP ke laptop.
Di kondisi itu `isInternetReachable` bernilai `false`, padahal API bisa dihubungi. Kalau kamu memakai tanda
itu, semua query akan dijeda selamanya.

</Callout>

## Query key factory

<Callout type="analogi" title="Seperti label rak di perpustakaan kampus">

Petugas perpustakaan menempel label di setiap rak, misalnya "Lantai 2 / Komputer / Basis Data". Kalau tiap
petugas menulis label dengan gayanya sendiri, ada yang menulis "Basis data", ada yang "Basdat". Buku jadi
sulit ditemukan. Karena itu perpustakaan memakai satu cetakan label resmi.

Label bertingkat juga memudahkan perintah massal. "Rapikan semua rak Lantai 2" mengenai semua rak di lantai
itu. "Rapikan rak Lantai 2 / Komputer / Basis Data" hanya mengenai satu rak.

- Label rak = query key
- Cetakan label resmi = **query key factory** (`taskKeys`)
- Perintah "semua rak Lantai 2" = pencocokan key berdasarkan **awalan**

</Callout>

Query key adalah alamat data di cache. Kalau key ditulis manual di banyak tempat, cepat atau lambat ada salah
ketik. Satu layar menulis `["task", id]`, layar lain menulis `["tasks", id]`. Keduanya tidak pernah bertemu di
cache. Solusinya adalah satu objek **factory** (pabrik pembuat key) yang menjadi satu-satunya sumber key untuk
fitur tugas.

Buat file `src/features/tasks/queries.js`. Bagian pertama berisi key dan fungsi bantu:

```js title="src/features/tasks/queries.js" showLineNumbers
import { Alert } from "react-native";
import { useInfiniteQuery, useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
import { apiFetch } from "../../lib/api";

export const PAGE_SIZE = 10;

export const taskKeys = {
  all: ["tasks"],
  lists: () => [...taskKeys.all, "list"],
  list: (filters) => [...taskKeys.lists(), filters],
  details: () => [...taskKeys.all, "detail"],
  detail: (id) => [...taskKeys.details(), id],
};

function toQueryString(params) {
  return Object.entries(params)
    .filter(([, value]) => value !== undefined && value !== null && value !== "")
    .map(([key, value]) => `${encodeURIComponent(key)}=${encodeURIComponent(value)}`)
    .join("&");
}
```

Isi bagian ini:

- `PAGE_SIZE` adalah jumlah tugas per halaman.
- `taskKeys` berisi fungsi-fungsi pembuat key. Setiap key dibangun dari key di atasnya, jadi semuanya
  berawalan `"tasks"`.
- `toQueryString` mengubah objek filter menjadi teks query di URL (bagian setelah tanda `?`). Nilai kosong
  dibuang.

Kalau dicoba, hasilnya seperti ini:

```js
console.log(taskKeys.list({ status: "TODO" }));
// → [ 'tasks', 'list', { status: 'TODO' } ]
console.log(taskKeys.detail(5));
// → [ 'tasks', 'detail', 5 ]
console.log(toQueryString({ status: "TODO", q: "basis data", courseId: undefined, page: 1 }));
// → status=TODO&q=basis%20data&page=1
```

Bentuk bertingkat ini berguna karena `invalidateQueries`, `cancelQueries`, dan fungsi sejenis mencocokkan key
berdasarkan **awalan**. Filter `["tasks"]` mengenai semua key yang dimulai dengan `"tasks"`:

| Filter `queryKey` | `["tasks","list",{}]` | `["tasks","list",{status:"DONE"}]` | `["tasks","detail",5]` |
| --- | --- | --- | --- |
| `taskKeys.all` | cocok | cocok | cocok |
| `taskKeys.lists()` | cocok | cocok | tidak |
| `taskKeys.list({ status: "DONE" })` | tidak | cocok | tidak |
| `taskKeys.detail(5)` | tidak | tidak | cocok |

Objek di dalam key juga dicocokkan **sebagian**. Filter `taskKeys.list({})` ternyata mengenai *semua* daftar,
karena objek kosong dianggap cocok dengan objek apa pun. Kalau kamu hanya ingin tepat satu key, tambahkan
`exact: true`, misalnya `invalidateQueries({ queryKey: taskKeys.list({}), exact: true })`.

Urutan properti di dalam objek key tidak berpengaruh. `{ status, q }` dan `{ q, status }` dianggap key yang
sama. Tipe data **berpengaruh**. Angka `5` dan teks `"5"` adalah dua key berbeda. Ingat ini, karena
`useLocalSearchParams` (hook Expo Router untuk membaca parameter di alamat layar) selalu memberi teks.

`toQueryString` ditulis manual dengan `encodeURIComponent`, fungsi yang mengubah spasi dan karakter khusus
supaya aman di URL. Kita tidak memakai `URLSearchParams` karena versinya di React Native belum lengkap.

## useQuery untuk detail tugas

Tambahkan hook pertama di `queries.js`:

```js title="src/features/tasks/queries.js"
export function useTask(id) {
  return useQuery({
    queryKey: taskKeys.detail(id),
    queryFn: async ({ signal }) => {
      const json = await apiFetch(`/api/tasks/${id}`, { signal });
      return json.data;
    },
  });
}
```

Dua hal kecil yang besar artinya:

- `queryFn` menerima `signal`. TanStack Query membatalkan request saat tidak ada lagi yang membutuhkannya,
  jadi `AbortController` manual tidak diperlukan.
- `queryFn` **harus mengembalikan nilai selain `undefined`**. Kita mengembalikan `json.data` sehingga cache
  berisi objek tugas, bukan amplop `{ data }`.

## useInfiniteQuery untuk daftar tugas

API pendamping mengembalikan daftar per halaman: `{ data, meta: { page, limit, total, totalPages } }`, dengan
`limit` maksimal 50. Daripada memuat `limit=50` sekaligus, kita memuat 10 tugas per halaman dan menambah
halaman saat pengguna menggulir ke bawah. Ini pekerjaan `useInfiniteQuery`:

```js title="src/features/tasks/queries.js"
export function useTasks(filters = {}) {
  return useInfiniteQuery({
    queryKey: taskKeys.list(filters),
    queryFn: ({ pageParam, signal }) =>
      apiFetch(`/api/tasks?${toQueryString({ ...filters, page: pageParam, limit: PAGE_SIZE })}`, { signal }),
    initialPageParam: 1,
    getNextPageParam: (lastPage) =>
      lastPage.meta.page < lastPage.meta.totalPages ? lastPage.meta.page + 1 : undefined,
  });
}
```

- `initialPageParam` **wajib** di v5. Nilainya menjadi `pageParam` untuk halaman pertama.
- `getNextPageParam` menerima halaman terakhir dan mengembalikan nomor halaman berikutnya, atau `undefined`
  kalau sudah habis. `undefined` membuat `hasNextPage` bernilai `false`.
- Di sini `queryFn` mengembalikan seluruh amplop `{ data, meta }` karena `meta` dibutuhkan
  `getNextPageParam`.

Bentuk `data` dari `useInfiniteQuery` bukan array tugas, melainkan `{ pages, pageParams }`. Dengan 10 tugas
seed dan `PAGE_SIZE` sementara diubah ke 4, setelah menggulir sampai habis isinya seperti ini:

```txt
pageParams: [1, 2, 3]
pages[0]: 4 tugas, meta { page: 1, limit: 4, total: 10, totalPages: 3 } -> next 2
pages[1]: 4 tugas, meta { page: 2, limit: 4, total: 10, totalPages: 3 } -> next 3
pages[2]: 2 tugas, meta { page: 3, limit: 4, total: 10, totalPages: 3 } -> next undefined
hasNextPage: false
```

Sekarang refactor layar daftar. Perhatikan berapa banyak yang hilang:

### Infinite scroll dengan onEndReached

`FlatList` memanggil `onEndReached` saat jarak ke ujung daftar kurang dari `onEndReachedThreshold` kali tinggi
layar (di sini setengah layar). Event itu bisa terpanggil beberapa kali berturut-turut, jadi penjaga
`hasNextPage && !isFetchingNextPage` wajib ada. Tanpa penjaga itu, halaman yang sama bisa diminta dua kali.
Materi dasar `FlatList` ada di [pelajaran FlatList](/belajar/react-native/flatlist).

### Pull-to-refresh dengan refetch

`refetch()` pada infinite query mengambil ulang **semua halaman yang sudah dimuat**, berurutan dari halaman 1,
supaya urutan dan isinya konsisten. `refetch` tidak melempar error secara bawaan, sehingga
`setRefreshing(false)` pasti dijalankan.

Kenapa tidak memakai `isRefetching` dari hook saja? Karena nilai itu juga `true` saat refetch otomatis berjalan,
misalnya ketika aplikasi kembali aktif. Spinner pull-to-refresh akan muncul tiba-tiba padahal pengguna tidak
menarik layar. State `refreshing` lokal memastikan spinner hanya muncul untuk tarikan pengguna.

`useFocusEffect` juga ikut hilang. Kita tidak perlu lagi memaksa refetch setiap kali layar daftar mendapat
fokus, karena mutation akan menandai cache daftar sebagai basi tepat ketika datanya berubah.

## useMutation dan invalidateQueries untuk create dan update

Query untuk **membaca**, mutation untuk **mengubah**. `useMutation` tidak berjalan otomatis. Ia memberimu fungsi
`mutate` beserta state `isPending`, `error`, dan `data` untuk satu operasi tulis.

```js title="src/features/tasks/queries.js"
export function useCreateTask() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (input) => {
      const json = await apiFetch("/api/tasks", { method: "POST", body: input });
      return json.data;
    },
    onSuccess: (task) => {
      queryClient.setQueryData(taskKeys.detail(task.id), task);
      return queryClient.invalidateQueries({ queryKey: taskKeys.lists() });
    },
  });
}

export function useUpdateTask() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async ({ id, input }) => {
      const json = await apiFetch(`/api/tasks/${id}`, { method: "PATCH", body: input });

    },
```

Dua strategi dipakai bersamaan:

- **`setQueryData`**: server sudah mengirim tugas versi terbaru (bentuknya sama dengan `GET /api/tasks/:id`,
  lengkap dengan `course` dan `attachments`), jadi kita taruh langsung di cache detail. Layar detail langsung
  menampilkan versi baru tanpa request tambahan.
- **`invalidateQueries`**: untuk daftar kita tidak tahu tugas baru jatuh di halaman berapa, apalagi kalau ada
  filter. Maka semua daftar ditandai basi. Daftar yang sedang tampil langsung diambil ulang, sedangkan daftar
  yang tidak aktif diambil ulang saat dipakai lagi.

`onSuccess` **mengembalikan** promise dari `invalidateQueries`. Akibatnya mutation tetap `isPending` sampai
daftar selesai disegarkan. Saat layar form ditutup, daftar di belakangnya sudah berisi tugas baru.

## Optimistic delete dengan onMutate, onError, dan onSettled

Di [Delete & Optimistic Update](/belajar/fullstack/delete-optimistic) kamu menghapus tugas dari state lebih
dulu, lalu mengembalikannya kalau server menolak. Polanya sama dengan TanStack Query, hanya saja sekarang yang
diubah adalah **cache**, dan cache itu bisa berisi beberapa daftar sekaligus (semua filter, semua halaman).

```js title="src/features/tasks/queries.js"
function removeTaskFromPages(old, id) {
  if (!old) return old;
  return {
    ...old,
    pages: old.pages.map((page) => ({
      ...page,
      data: page.data.filter((task) => task.id !== id),
    })),
  };
}

export function useDeleteTask() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (id) => apiFetch(`/api/tasks/${id}`, { method: "DELETE" }),
    onMutate: async (id) => {
      await queryClient.cancelQueries({ queryKey: taskKeys.lists() });
      const previousLists = queryClient.getQueriesData({ queryKey: taskKeys.lists() });
      queryClient.setQueriesData({ queryKey: taskKeys.lists() }, (old) => removeTaskFromPages(old, id));
      return { previousLists };
    },
    onError: (error, id, context) => {
      context?.previousLists.forEach(([queryKey, data]) => {
        queryClient.setQueryData(queryKey, data);
      });
      Alert.alert("Gagal menghapus tugas", error.message);
    },
    onSuccess: (data, id) => {
      queryClient.removeQueries({ queryKey: taskKeys.detail(id) });
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: taskKeys.lists() }),
  });
}
```

<Flow nodes={["Tekan Hapus", "onMutate", "DELETE /api/tasks/:id", "onSuccess / onError", "onSettled"]} labels={["mutate(id)", "cache sudah tanpa tugas", "204 atau error", "selalu jalan"]} caption="Urutan callback optimistic delete" />

| Langkah | Tujuan |
| --- | --- |
| `cancelQueries` | Batalkan refetch daftar yang sedang berjalan supaya tidak menimpa perubahan optimis kita dengan data lama |
| `getQueriesData` | Ambil snapshot semua daftar dalam bentuk array `[queryKey, data]` |
| `setQueriesData` | Hapus tugas dari setiap halaman di setiap daftar. Updater yang mengembalikan `undefined` tidak mengubah apa pun |
| `return { previousLists }` | Nilai ini diteruskan ke `onError` (argumen ketiga) dan `onSettled` (argumen keempat) |
| `onError` | Kembalikan snapshot dan beri tahu pengguna |
| `onSuccess` | Buang cache detail tugas yang sudah tidak ada |
| `onSettled` | Sukses atau gagal, sinkronkan ulang daftar dengan server |

`Alert` sengaja diletakkan di hook, bukan di layar. Kalau pengguna sudah berpindah layar saat server menolak,
pesan tetap muncul dan rollback tetap terjadi. `apiFetch` mengembalikan `undefined` untuk respons 204, dan itu
aman karena ini mutation, bukan query.

<Callout type="tip" title="Kalau kamu punya tombol Urungkan">

Kalau di pelajaran delete kamu menambahkan jeda "Urungkan" sebelum benar-benar menghapus, pertahankan pola
itu: sembunyikan tugas dari cache dengan `setQueriesData`, lalu panggil `deleteTask.mutate(id)` hanya setelah
jeda habis. Kalau pengguna menekan Urungkan, cukup panggil `invalidateQueries` untuk daftar.

</Callout>

```js title="src/features/tasks/queries.js"
function patchTaskInPages(old, id, input) {
  if (!old) return old;
  return {
    ...old,
    pages: old.pages.map((page) => ({
      ...page,
      data: page.data.map((task) => (task.id === id ? { ...task, ...input } : task)),
    })),
  };
}

export function useUpdateTask() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async ({ id, input }) => {
      const json = await apiFetch(`/api/tasks/${id}`, { method: "PATCH", body: input });
      return json.data;
    },
    onMutate: async ({ id, input }) => {
      await queryClient.cancelQueries({ queryKey: taskKeys.lists() });
      await queryClient.cancelQueries({ queryKey: taskKeys.detail(id) });
      const previousLists = queryClient.getQueriesData({ queryKey: taskKeys.lists() });
      const previousTask = queryClient.getQueryData(taskKeys.detail(id));
      queryClient.setQueriesData({ queryKey: taskKeys.lists() }, (old) => patchTaskInPages(old, id, input));
      queryClient.setQueryData(taskKeys.detail(id), (old) => (old ? { ...old, ...input } : old));
      return { previousLists, previousTask };
    },
    onError: (error, { id }, context) => {
      context?.previousLists.forEach(([queryKey, data]) => queryClient.setQueryData(queryKey, data));
      queryClient.setQueryData(taskKeys.detail(id), context?.previousTask);
      Alert.alert("Gagal menyimpan tugas", error.message);
    },
    onSuccess: (task) => {
      queryClient.setQueryData(taskKeys.detail(task.id), task);
    },
    onSettled: (data, error, { id }) =>
      Promise.all([
        queryClient.invalidateQueries({ queryKey: taskKeys.lists() }),
        queryClient.invalidateQueries({ queryKey: taskKeys.detail(id) }),
      ]),
  });
}
```

Pemakaian dari kartu: `updateTask.mutate({ id: task.id, input: { status: "DONE" } })`. Kita menggabungkan
`input` ke objek lama dengan spread, sehingga field lain seperti `course` tetap ada. Kalau `previousTask`
bernilai `undefined` (detail belum pernah dibuka), `setQueryData` dengan nilai `undefined` tidak mengubah apa
pun. Semua kunci tetap berasal dari `taskKeys`.

</Solution>

## Ringkasan

- **Server state** (data milik API) butuh cache, refetch, retry, dan sinkronisasi. Itulah pekerjaan
  TanStack Query, bukan `useState`.
- `src/lib/query-client.js` berisi satu `QueryClient` dengan `staleTime` 30 detik dan retry yang melewati
  error 4xx, ditambah `focusManager` (lewat `AppState`) dan `onlineManager` (lewat `expo-network` dan
  `isConnected`). `QueryClientProvider` membungkus `<Stack>` di root layout.
- `taskKeys` adalah satu-satunya sumber query key. Pencocokan berdasarkan awalan, dan tipe data di dalam key
  berpengaruh (`Number(id)`).
- `useTask` memakai `useQuery`, sedangkan `useTasks` memakai `useInfiniteQuery` dengan `initialPageParam`
  dan `getNextPageParam` dari `meta`. `FlatList` memanggil `fetchNextPage` lewat `onEndReached`, dan
  pull-to-refresh memanggil `refetch`.
- Mutation create dan update memakai `setQueryData` untuk detail dan `invalidateQueries` untuk semua daftar.
  Delete memakai pola optimistic `onMutate` → `onError` (rollback) → `onSettled` (invalidate).
- Layar kini hanya berisi UI. Logika data tinggal di `src/features/tasks/queries.js`.
